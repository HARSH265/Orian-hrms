
### **Project "Orion" HRMS — Phase 1 Development Log**

**Objective:** To build the foundational layers of the Orion HRMS, focusing on core authentication, a scalable frontend architecture, and the complete "Employee," "Manager," and "Admin" user-facing features.

---

### **Phase 1: Features & Capabilities Completed**

At the conclusion of Phase 1, the Orion application has a robust set of features across three primary roles, supported by a modern technology stack.

#### **A. Core Technology & Architecture:**
*   **Backend:** Node.js/Express server with a MongoDB database.
*   **Frontend:** React application built with a professional-grade architecture.
*   **State Management:** Redux Toolkit implemented for centralized, predictable state management.
*   **UI/UX:** Ant Design component library used for a clean, consistent, and responsive user interface.
*   **API Layer:** A centralized Axios client with request/response interceptors for handling authentication and token refreshing automatically.
*   **Code Structure:** A clean, modular structure separating features into slices, thunks, services, pages, and components.

#### **B. Role-Based Feature Implementation:**

**1. Foundational System (Authentication & Security):**
*   **Secure User Login:** Endpoint for authenticating users via email and password.
*   **JWT-Based Authentication:** Implemented a secure strategy using short-lived `Access Tokens` and long-lived, `httpOnly` `Refresh Tokens`.
*   **Persistent Sessions:** Users remain logged in even after a page refresh.
*   **Automatic Token Refresh:** The frontend seamlessly handles expired access tokens by using the refresh token to get a new one, providing an uninterrupted user experience.
*   **Secure Logout:** A clean logout process that clears tokens from the state, `localStorage`, and API client headers.
*   **Role-Based Access Control (RBAC):** Backend routes are protected by middleware that authorizes access based on user roles (`employee`, `manager`, `hr`, `super-admin`).
*   **Conditional UI Rendering:** The frontend UI (e.g., navbar links) dynamically changes based on the logged-in user's role.

**2. EMPLOYEE Role (Self-Service Module):**
*   **Profile Management:**
    *   Users can view their complete profile data.
    *   Users can edit and update their own non-sensitive information (phone, address).
*   **Leave Management:**
    *   Users can apply for new leave requests through a dedicated form.
    *   Users can view a complete history of their past leave requests and their current status (Pending, Approved, Denied).

**3. MANAGER Role (Team Management Module):**
*   **Team Leave Approvals:**
    *   Managers can view a list of all leave requests submitted by their direct reports.
    *   Managers have an interface with "Approve" and "Deny" buttons to action pending requests.
    *   The system provides real-time feedback, updating the status and UI upon a manager's action.

**4. ADMIN Role (System Administration Module):**
*   **User Management:**
    *   Admins can view a table of all users in the entire system.
    *   Admins have a UI to create new users with specific roles, job titles, and departments, completely removing the need for manual database entry.

### **Part 2: Challenges Faced & Solutions Implemented**

Phase 1 involved overcoming several critical, real-world development challenges. These were not simple syntax errors but complex issues in logic, timing, and architecture.

**1. Challenge: Cross-Origin Resource Sharing (CORS) Error**
*   **Problem:** The frontend (`localhost:3000`) was blocked by the browser from making requests to the backend (`localhost:5001`).
*   **Solution:** We installed and configured the `cors` middleware on the backend server, explicitly allowing the frontend's origin and enabling `credentials` to permit the sending of secure cookies.

**2. Challenge: Inconsistent User Data on Login vs. Refresh**
*   **Problem:** The user's `email` was missing on initial login because the `/login` endpoint returned only partial data.
*   **Solution:** We re-architected the login flow to be more robust. The `loginUser` thunk now authenticates, gets the token, and then immediately **chains a dispatch to the `getMe` thunk**. This ensures the full, consistent user profile is always fetched from the `/profile` endpoint, creating a single source of truth.

**3. Challenge: Race Condition Leading to Auto-Logout**
*   **Problem:** When chaining thunks, the `getMe` call was dispatched before the `loginUser` reducer could update the Redux store with the new token, causing the `getMe` request to be unauthenticated and fail.
*   **Solution:** We solved this timing issue by having the `loginUser` thunk **manually set the default `Authorization` header** on our global `api` instance (`api.defaults.headers.common['Authorization'] = ...`) immediately after receiving the token. This guaranteed that the subsequent `getMe` request was authenticated.

**4. Challenge: Infinite Loop During Token Refresh**
*   **Problem:** The Axios interceptor, designed to catch `401` errors, was also intercepting the `401` error from the `/auth/refresh` call itself, causing it to try and refresh indefinitely.
*   **Solution:** We broke the loop by using a **"clean" `axios` instance** (imported directly) for the refresh token API call. This call bypassed our custom interceptor. We also added `{ withCredentials: true }` to ensure the `httpOnly` cookie was sent.

**5. Challenge: Circular Dependencies**
*   **Problem:** The application crashed with a `Cannot access '...' before initialization` error because `api.js`, `store.js`, and `authSlice.js` were all importing each other in a loop.
*   **Solution:** We refactored the code by creating a dedicated **`apiInterceptors.js`** file. This logic was then called from the main `index.js` file *after* both the `store` and `api` instance had been independently created, breaking the import cycle.

**6. Challenge: Database Data Type Mismatch (`ObjectId` vs. `String`)**
*   **Problem:** The Manager's team page was empty because the `manager` field in the employee's user document was incorrectly saved as a `String` instead of a MongoDB `ObjectId`.
*   **Solution:** We used MongoDB Compass to manually edit the document and **correct the data type** of the `manager` field. This reinforced the importance of data integrity and how subtle database errors can manifest as "missing data" on the frontend.

#### **Part 2: Challenges Faced & Solutions Implemented**

*   **Challenge: The "Silent Failure" of the Welcome Wizard.**
    *   **Problem:** The wizard would not advance to the next step, despite the API call succeeding and no errors appearing in the console.
    *   **Root Cause:** A complex React lifecycle issue. A Redux state update was causing the parent `<WizardGuard>` to re-render, which in turn unmounted and remounted the `<WelcomeWizardPage>`, resetting its internal step counter.
    *   **Solution:** We implemented a fundamental React pattern: **"lifting state up."** The `currentStep` state was moved from the wizard page to the parent `WizardGuard` component and passed down as props. This preserved the state across re-renders and fixed the bug.

*   **Challenge: Circular Dependency with Redux Thunks & Slices.**
    *   **Problem:** An attempt to dispatch a synchronous action from within a thunk created a circular dependency (`thunk` importing `slice` and `slice` importing `thunk`), causing a compilation error.
    *   **Solution:** We refactored the architecture to follow best practices. The thunk was simplified to only handle the async API call and return a value. The slice was then updated with a proper `extraReducer` case to handle the thunk's `fulfilled` state and update the Redux store.

*   **Challenge: Logical Gaps in High-Level Role Permissions.**
    *   **Problem:** Rigorous testing revealed that features designed for `managers` (like "Team Expenses") were failing for `hr` and `super-admin` roles, creating "orphaned" requests for them.
    *   **Solution:** We refactored the UI and backend logic to be truly **role-aware**. We created unified "hub" pages (like `HighLevelTasksPage` and `ExpenseApprovalPage`) that use conditional logic to fetch and display the correct data (e.g., "my team's data" for a manager vs. "all system data" for an admin).

*   **Challenge: Configuration Errors with Third-Party Libraries.**
    *   **Problem:** The Ant Design Charts library was throwing cryptic runtime errors (`Unknown position: middle`, `Unknown Component: shape.inner`).
    *   **Solution:** We systematically debugged by isolating the configuration objects and consulting documentation, correcting invalid property names and values (`position`, `label.type`) until the charts rendered correctly.
